# Проследить текущий путь диагностических данных ошибочной Проверки

## Question

Какие диагностические данные возникают на каждом этапе Проверки, какие из них доходят до `PageProbeResult`, SQLite, HTTP API, UI, Telegram и NDJSON-лога, где именно данные теряются, и какие существующие механизмы ротации и редактирования чувствительных значений можно переиспользовать?

## Expected asset

`.scratch/monitoring-failure-diagnostics/research/01-current-failure-diagnostics.md`

## Answer

Исследование сохранено в [Current failure-diagnostics path](../research/01-current-failure-diagnostics.md).

`PageProbeFailure` уже содержит код и сообщение, этап, эффективный URL, HTTP-статус, общие и поэтапные timings, а для применимых ошибок — поле и индекс селектора. Точная точка потери находится в `MonitorService`: перед `MonitorStore.failCheck` полный результат сужается до `{ code, message }`.

SQLite сохраняет отдельные записи исходной и Повторной проверки и связывает их через существующую retry-модель, но диагностических полей кроме кода и сообщения в схеме нет. Поэтому HTTP API, UI, финальное уведомление и Telegram восстановить отброшенные данные не могут. `notification_deliveries.diagnostic` относится только к stdout/stderr Telegram sender и не является диагностикой Проверки.

NDJSON-лог сейчас не получает события ошибочных Проверок. Его можно переиспользовать для небольшого allowlisted события: он рекурсивно редактирует известные секреты и ротируется по 10 MiB с 20 поколениями. Однако его `write` синхронный и может выбросить ошибку, redaction основан на ключах и шаблонах, а размер отдельного события не ограничен. Поэтому запись на пути Проверки должна быть best-effort, с явным перечнем безопасных скалярных полей; существующая redaction служит только дополнительной защитой.

Наиболее ранний пригодный seam — переход `MonitorService → MonitorStore.failCheck`: там одновременно доступны идентификаторы Проверки и полный `PageProbeFailure`. Существующая идентичность Проверки и retry-chain достаточна для корреляции, отдельный correlation ID не требуется.
