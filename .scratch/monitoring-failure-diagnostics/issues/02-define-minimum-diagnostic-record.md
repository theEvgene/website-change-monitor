# Определить минимальную диагностическую запись ошибочной Проверки

## Question

Какие поля обязательны для расследования ошибочной Проверки, где находится источник истины, как запись коррелируется с Монитором, Проверкой, попыткой и Повторной проверкой, и какие данные должны оставаться только пользовательским сообщением?

## Answer

Для каждой Проверки, завершившейся с `result = error`, создаётся не более одной связанной **Диагностики Проверки**. Успешные Проверки (`baseline`, `no_change`, `change`) диагностическую запись не создают.

### Источник истины

Источник истины — SQLite-запись с уникальной связью по `check_id` и каскадным удалением вместе с Проверкой. NDJSON не дублирует эту запись. Это сохраняет точную корреляцию, позволяет применить срок хранения и оставляет возможность позднее безопасно открыть или экспортировать диагностику.

Существующие данные не дублируются:

- `checkId`, `monitorId`, вид Проверки, `startedAt`, `completedAt`, `errorCode`, `errorMessage` и `isFinalError` читаются из Проверки;
- исходная и Повторная проверки связываются существующим `retry_of_check_id`;
- отдельный correlation ID, копия имени Монитора, исходного URL, кода и сообщения ошибки не нужны.

### Минимальные поля Диагностики Проверки

- `check_id` — обязательный уникальный внешний ключ;
- `recorded_at` — обязательное время создания диагностической записи и опорная точка срока хранения;
- `stage` — обязательный ограниченный этап ошибки; существующие этапы `PageProbe` переиспользуются, а ошибки после исследования страницы получают отдельный прикладной этап вроде `snapshot`;
- `final_url` — необязательный эффективный URL после redirect, если он известен;
- `http_status` — необязательный целочисленный HTTP-статус главного документа;
- `total_ms` — обязательная общая длительность известной части Проверки;
- `navigation_ms`, `target_ms`, `scroll_ms`, `stability_ms`, `extraction_ms` — необязательные неотрицательные длительности этапов;
- `selector_field` и `selector_index` — необязательная пара для ошибки конкретного Целевого селектора или Селектора исключения.

Неизвестное значение хранится как `NULL`, а не как выдуманный ноль или фиктивный статус. Для synthetic orchestration timeout допустимы только известные `stage` и `total_ms`. Ошибка формирования Снимка создаёт запись с прикладным этапом и без HTTP/selector-полей.

### Запрещённое содержимое

В минимальную запись не входят тело страницы, HTML, снимок экрана, HAR/trace, request/response headers, cookies, credentials, локальные исключения/stack trace и произвольный текст браузера. Пользовательское `errorMessage` остаётся в Проверке; Диагностика Проверки содержит только ограниченные структурированные значения.

### Граница формирования

Для ошибки `PageProbe` запись проецируется из полного `PageProbeFailure` на границе `MonitorService → MonitorStore.failCheck`, пока доступны и идентичность Проверки, и диагностический envelope. Для snapshot/application-level ошибок тот же `failCheck` получает явно сформированную прикладную диагностику. Правила атомарности, best-effort-поведения и удаления старше 14 дней определяет следующий фронтир.

## Comments

- Пользователь: диагностические записи нужны только для ошибочных итераций мониторинга; успешные Проверки не должны создавать такие записи.
- Пользователь: SQLite — единственный источник истины; дублирование диагностической записи в NDJSON не требуется.
