# Спроектировать workflow расследования и проверяемый контракт

## Question

Как пользователь или агент находит диагностику конкретной ошибочной Проверки, нужен ли просмотр или экспорт через UI/API, какие сценарии требуют опциональных артефактов, и какими автоматизированными тестами и критериями приёмки доказывается полнота, безопасность и согласованность решения?

## Answer

### Workflow расследования

Диагностика предназначена для технического анализа агентом. Изменения UI, отдельная страница, модальное окно и экспорт файлов для MVP не нужны.

1. Агент находит ошибочную Проверку и её `checkId` через существующий `GET /api/checks` либо `GET /api/monitors/{monitorId}/checks`.
2. Агент запрашивает `GET /api/checks/{checkId}/diagnostics`.
3. Endpoint возвращает только документированный allowlisted контракт. Он не читает и не возвращает сырые browser-артефакты, NDJSON или внутренние исключения.
4. Endpoint входит в существующую OpenAPI-схему, поэтому способ его вызова и структура ответа доступны агенту через `/openapi.json`.

Для существующей Проверки ответ имеет одно из четырёх детерминированных состояний:

- `available` — диагностическая запись найдена; поле `diagnostic` содержит безопасные структурированные значения;
- `not_applicable` — Проверка не завершилась ошибкой, поэтому диагностика для неё по правилам не создавалась;
- `expired` — ошибочная Проверка старше 14 суток и её диагностика уже удалена;
- `unavailable` — ошибочная Проверка ещё находится внутри срока хранения, но best-effort запись отсутствует или не была сформирована.

Во всех этих случаях endpoint отвечает `200`, возвращает `checkId`, `availability` и `diagnostic` (`null`, кроме `available`). Это не смешивает штатное отсутствие, истечение срока хранения и деградацию записи. Несуществующий `checkId` получает обычный `404 not_found`. Доступ остаётся ограничен существующей моделью локального HTTP-сервера; новый обход её host/origin-защиты не создаётся.

При `available` API может объединить Диагностику Проверки с уже существующими безопасными полями Проверки, необходимыми расследованию (`monitorId`, вид, времена начала/завершения, `errorCode`, `errorMessage`, финальность и retry-связь), но эти значения не дублируются в диагностической таблице. Поля диагностического объекта точно соответствуют минимальной записи из билета 02 и правилам нормализации из билета 03.

### Артефакты и глубина диагностики

Отдельный углублённый режим и опциональные артефакты в MVP не вводятся. HTML, тела ответов, headers, cookies, screenshots, HAR/trace, stack traces и произвольный browser output не сохраняются и не выдаются API. Если минимальной структурированной записи окажется недостаточно для реального класса инцидентов, расширение рассматривается отдельно на основании конкретного обезличенного пробела, а не заранее.

### Границы реализации

- Общая закрытая структура диагностики определяется на application/persistence-границе и переиспользуется при записи и в HTTP-ответе; отдельная HTTP-модель не должна заново интерпретировать browser failure.
- `MonitorService` передаёт allowlisted диагностику вместе с ошибочным переходом, а persistence сохраняет её best-effort отдельно от канонического результата Проверки.
- Store предоставляет точечное чтение по `checkId` и очистку по `recorded_at`; HTTP-слой только вычисляет состояние доступности и сериализует типизированный результат.
- Очистка запускается при старте и периодически в существующем lifecycle приложения, без отдельного фонового сервиса.
- Ни Telegram, ни существующие journal/history responses, ни UI для этой возможности не меняются.

### Автоматизированный контракт

Минимальный набор тестов:

1. Миграция создаёт таблицу с уникальным FK `check_id`, каскадным удалением, ограниченными типами и индексом для очистки по `recorded_at`.
2. Каждая ветка ошибочной Проверки (`PageProbe`, snapshot/application error и восстановление прерванной Проверки) создаёт не более одной корректно связанной диагностики.
3. `baseline`, `no_change` и `change` не создают диагностических строк.
4. Все допустимые `stage`, timings, HTTP status и selector location сохраняются; неизвестные значения становятся `NULL`.
5. `finalUrl` очищается от credentials, query и fragment; недопустимые enum, диапазоны и строки не попадают в базу.
6. Ошибка формирования или вставки диагностики не меняет Результат проверки, retry, финальное Уведомление и работу worker; operational fallback не содержит payload.
7. Очистка удаляет только записи старше 14 суток, сохраняет граничную запись, не меняет Проверки и идемпотентна.
8. Очистка выполняется при запуске и повторяется не реже раза в 24 часа непрерывной работы; её ошибка не блокирует запуск или Проверки.
9. HTTP-тесты через Fastify `inject` покрывают `available`, `not_applicable`, `expired`, `unavailable` и `404`, включая отсутствие запрещённых полей.
10. OpenAPI contract test фиксирует маршрут, operation ID, response schema и используемые enum.
11. Интеграционный тест проходит полный путь `PageProbeFailure → MonitorService → SQLite → diagnostics endpoint` и доказывает совпадение значений на всех границах.
12. Тест удаления Монитора/Проверки подтверждает каскадное удаление диагностики без отдельного остатка или архива.

### Критерии приёмки

- Для любой сохранённой ошибочной Проверки внутри 14 суток агент получает по `checkId` достаточную структурированную диагностику либо явное состояние `unavailable`.
- Успешные Проверки не увеличивают объём диагностического хранилища.
- Агент различает неприменимость, истёкший срок хранения, деградацию записи и неизвестный `checkId`.
- Endpoint и OpenAPI не раскрывают ничего сверх согласованного allowlist.
- Истечение срока удаляет только диагностику; факт ошибки и retry-история остаются доступны.
- Сбой необязательной диагностики или её очистки не влияет на мониторинг и уведомления.
- Реализация не содержит логики для конкретных сайтов и не вводит UI либо дополнительный формат экспорта.
