# Подробные Telegram-уведомления об Изменениях

Status: ready-for-agent

## Problem Statement

Website Change Monitor уже обнаруживает Изменения между последовательными Снимками и показывает их в локальном интерфейсе как двухколоночное Сравнение. Однако Telegram-уведомление сообщает только сам факт изменения и ссылку на исходную страницу. На телефоне пользователь не видит, какой текст появился или исчез, поэтому вынужден открывать страницу либо возвращаться к локальному интерфейсу и самостоятельно искать отличие.

На больших или часто обновляемых страницах исходное содержимое может измениться повторно до того, как пользователь его откроет. В результате важный удалённый фрагмент уже нельзя найти на текущей странице. Telegram-уведомление должно давать короткий, предметно-нейтральный ориентир непосредственно в чате, не превращаясь при этом в длинную копию всего Сравнения.

## Solution

Расширить существующее plain-text Telegram-уведомление об Изменении Подробностями Изменения, полученными из того же backend-Сравнения, которое использует интерфейс приложения. Уведомление идентифицирует страницу историческим именем Монитора, сохраняет безопасную ссылку на проверявшийся URL и показывает две непустые секции: «Добавлено» и «Удалено».

Отдельной секции «Изменено» не будет. Любая строка Сравнения, представленная как замена, раскладывается на удалённый старый фрагмент и добавленный новый. Это сохраняет простоту MVP и исключает ложное утверждение о смысловой связи между двумя строками.

Подробности ограничиваются общим бюджетом 300 Unicode-символов. Если присутствуют обе секции, каждая сначала получает по 150 символов, а неиспользованный остаток одной секции передаётся другой. При сокращении или неполном Сравнении пользователь видит явное пояснение: «…показана только часть изменений». Базовая идентификация и ссылка в этот бюджет не входят.

Если изменилась только структура отслеживаемой области, а полное Сравнение не обнаружило изменения видимого текста, Telegram сообщает: «Изменилась структура отслеживаемой области. Изменений видимого текста не обнаружено». Если подготовить Подробности невозможно, приложение записывает безопасную техническую ошибку и всё равно отправляет существующее базовое уведомление о факте Изменения со ссылкой.

Расписание Проверок, получение и хранение Снимков, локальный интерфейс, центр Уведомлений, настройки Telegram и существующие виды контрольных Уведомлений и Окончательных ошибок не меняются.

## User Stories

1. As a пользователь, I want to получить Telegram-уведомление с конкретными текстовыми отличиями so that я могу понять суть Изменения, не открывая локальный интерфейс.
2. As a пользователь, I want to видеть историческое имя Монитора в уведомлении so that я понимаю, какая отслеживаемая страница изменилась.
3. As a пользователь, I want to сохранить ссылку на исходную проверявшуюся страницу so that я могу сразу перейти к актуальному содержимому.
4. As a пользователь, I want to видеть появившийся текст в отдельной секции «Добавлено» so that новые фрагменты легко отличить от исчезнувших.
5. As a пользователь, I want to видеть исчезнувший текст в отдельной секции «Удалено» so that информация не теряется после удаления с исходной страницы.
6. As a пользователь, I want to видеть старую и новую строки предполагаемой замены как удаление и добавление so that приложение не придумывает недоказанную смысловую связь.
7. As a пользователь, I want to не видеть отдельную секцию «Изменено» so that MVP остаётся простым и однозначным.
8. As a пользователь, I want to видеть фрагменты в стабильном порядке Сравнения so that уведомления об одной и той же паре Снимков воспроизводимы.
9. As a пользователь, I want to не видеть пустые заголовки секций so that сообщение не содержит формулировок вроде «Удалено: ничего».
10. As a пользователь, I want to получать компактное сообщение so that его удобно читать на телефоне.
11. As a пользователь, I want to ограничить суммарный изменившийся текст 300 Unicode-символами so that большое Изменение не заваливает Telegram длинными сообщениями.
12. As a пользователь, I want to выделять добавлениям и удалениям по 150 символов при наличии обеих секций so that один вид Изменения не вытесняет другой.
13. As a пользователь, I want to передавать неиспользованный остаток бюджета другой секции so that короткое удаление не мешает показать больше полезного добавленного текста и наоборот.
14. As a пользователь, I want to видеть начало последнего неуместившегося фрагмента so that ограниченный бюджет используется для полезного ориентира.
15. As a пользователь, I want to видеть явный маркер сокращения so that частичный текст не воспринимается как полное описание Изменения.
16. As a пользователь, I want to видеть маркер неполноты при ограниченном backend-Сравнении so that приложение честно сообщает о возможных пропущенных фрагментах.
17. As a пользователь, I want to получить отдельное пояснение о структурном Изменении без видимого текстового Изменения so that уведомление не выглядит пустым или ошибочным.
18. As a пользователь, I want to не получать утверждение об отсутствии текстовых изменений при неполном Сравнении so that система не делает недоказанный вывод.
19. As a пользователь, I want to видеть Markdown-символы буквально so that произвольный текст страницы не ломает Telegram-сообщение.
20. As a пользователь, I want to видеть HTML-подобный текст буквально so that содержимое страницы не интерпретируется как разметка уведомления.
21. As a пользователь, I want to корректно видеть переносы строк so that многострочные фрагменты остаются читаемыми и принадлежат одному пункту.
22. As a пользователь, I want to не видеть управляющие символы и технический шум so that уведомление остаётся читаемым.
23. As a пользователь, I want to сохранять значимые внутренние пробелы, табы, регистр и пунктуацию so that Подробности не искажают исходный видимый текст.
24. As a пользователь, I want to не получать повреждённые Unicode-символы на границе бюджета so that emoji и другие символы вне BMP отображаются корректно.
25. As a пользователь, I want to получать уведомление только для фактически зафиксированного Изменения so that новая функция не создаёт дополнительных событий.
26. As a пользователь, I want to сохранить существующий режим контрольных Уведомлений so that сообщения о Проверках без Изменений продолжают зависеть только от его настройки.
27. As a пользователь, I want to сохранить существующий формат Окончательной ошибки so that Подробности Изменения не затрагивают сообщения другого вида.
28. As a пользователь, I want to получить базовое уведомление при ошибке загрузки Сравнения so that сбой новой функции не скрывает сам факт Изменения.
29. As a пользователь, I want to получить базовое уведомление при повреждённом или неподдерживаемом Снимке so that ошибка Подробностей не блокирует Telegram.
30. As a пользователь, I want to получить базовое уведомление при ошибке проекции или форматирования so that основное оповещение остаётся отказоустойчивым.
31. As a пользователь, I want to сохранить успешное Состояние доставки Telegram, если базовый fallback был доставлен so that интерфейс отражает фактическую отправку.
32. As a пользователь, I want to не потерять базовое уведомление даже при ошибке технического журнала so that отказ логирования не становится отказом доставки.
33. As a владелец приложения, I want to получить безопасную техническую запись об ошибке Подробностей so that проблему можно диагностировать без сохранения содержимого отслеживаемой страницы в логах.
34. As a владелец приложения, I want to не записывать в технический журнал Снимки, URL, полный diff или готовое сообщение so that локальные логи не накапливают лишнее пользовательское содержимое.
35. As a пользователь, I want to сохранить существующую защиту URL credentials so that уведомление не раскрывает встроенные учётные данные.
36. As a пользователь, I want to сохранить существующее поведение недоступного Telegram so that приложение продолжает выполнять Проверки в деградированном режиме.
37. As a пользователь, I want to не получать старые неотправленные сообщения задним числом so that новая функция не меняет best-effort модель доставки.
38. As a пользователь, I want to сохранить текущий локальный интерфейс и Сравнение без изменений so that Telegram-улучшение не расширяет UI-задачу.
39. As a пользователь, I want to сохранить текущие расписания и историю Мониторов so that улучшение текста Уведомления не влияет на мониторинг.
40. As a пользователь, I want to получать одинаковую классификацию добавлений и удалений в Telegram и локальном Сравнении so that два представления не противоречат друг другу.

## Implementation Decisions

- Единственным источником классификации остаётся существующее backend-Сравнение. Независимый Telegram diff или повторное сравнение исходного текста не создаётся.
- Telegram delivery job получает идентификатор Проверки из уже существующего события Уведомления. По нему непосредственно перед доставкой извлекается уже сохранённая пара Снимков.
- Схема SQLite не меняется: событие уже хранит идентификатор Проверки, а Проверка уже ссылается на прежний и новый Снимки.
- Подготовка Подробностей выполняется после commit. Она не входит в транзакцию завершения Проверки и не может откатить Результат проверки, Снимок, расписание или Уведомление.
- Добавляется один чистый Telegram-модуль с небольшим интерфейсом: он принимает результат общего Сравнения, возвращает упорядоченные массивы удалённого и добавленного текста, признак структурного Изменения и признак полноты, а затем формирует ограниченное plain-text представление.
- Равные строки игнорируются. Удаление попадает только в удалённые фрагменты, вставка — только в добавленные, а замена раскладывается в оба массива без установления связи между ними.
- Строка неполноты backend-Сравнения не превращается в пользовательский фрагмент; она отражается общим признаком неполноты.
- Структурное пояснение разрешено только при полном Сравнении, отсутствии текстовых фрагментов и наличии структурных Изменений.
- Секция «Добавлено» выводится перед секцией «Удалено». Пустые секции исключаются целиком.
- Фрагменты нормализуются в NFC, переводы строк приводятся к LF, управляющие C0/DEL-символы кроме LF и TAB заменяются пробелом, внешние пробельные символы удаляются. Пустые после нормализации фрагменты исключаются.
- Внутренние переносы сохраняются и визуально продолжают тот же bullet. Внутренние пробелы, табы, регистр и пунктуация дополнительно не нормализуются.
- Бюджет Подробностей равен 300 Unicode code points и не включает заголовки, bullet-префиксы, пустые строки, идентификацию, ссылку и маркер неполноты.
- При двух непустых секциях начальный бюджет составляет 150/150. Неиспользованный остаток передаётся другой секции. Одна непустая секция получает весь бюджет.
- Полностью помещающиеся фрагменты сохраняются. Последний непомещающийся фрагмент сокращается по Unicode code points; следующие фрагменты не выводятся.
- Маркер «…показана только часть изменений» выводится ровно один раз при сокращении либо неполном Сравнении.
- Сообщение остаётся plain text. Telegram `parse_mode`, Markdown/HTML escaping, изображения, файлы и внешняя LLM не используются.
- Безусловное ограничение всего сообщения 3000 символами удаляется, чтобы не отрезать ссылку и не скрывать неполноту. Существующее разбиение внешнего sender остаётся страховкой для необычно длинной базовой части, но не используется для расширения 300-символьных Подробностей.
- До расширенного форматирования dispatcher создаёт текущую базовую форму из заголовка, безопасной ссылки и тела Уведомления.
- Отсутствие пары Снимков или ошибка Сравнения, проекции либо форматирования перехватываются внутри Telegram-пути. После best-effort логирования sender получает заранее подготовленную базовую форму.
- Существующий NDJSON logger передаётся по runtime-цепочке от CLI до Telegram dispatcher. Новая система логирования или отдельный logging adapter не создаются.
- Техническое событие ошибки содержит только идентификаторы события и Проверки, стабильную стадию, имя ошибки и короткое безопасное сообщение. Снимки, URL, фрагменты, полный diff и итоговый Telegram-текст не логируются.
- Ошибка записи logger также перехватывается и не блокирует базовую доставку.
- Форматы контрольного Уведомления и Окончательной ошибки не проходят через новый модуль и остаются прежними.
- Центр Уведомлений, browser notifications, REST/SSE/OpenAPI и React UI не меняются.
- Существующий внешний `telegram-alert-bus` не меняется и не получает новых полей: он продолжает принимать прежний строгий JSON и отправлять plain text.
- Новые зависимости и ADR не требуются.

## Testing Decisions

- Главный чистый тестовый шов — интерфейс модуля Подробностей Изменения. Тесты передают `SnapshotComparison` и проверяют только возвращаемую проекцию или окончательный plain-text результат, не приватные helpers распределения бюджета.
- Главный интеграционный шов — Telegram dispatcher с временной настоящей SQLite, fake executable, фиксированными часами и fake NDJSON logger. Он доказывает путь от зафиксированной Проверки и двух Снимков до JSON, фактически переданного sender.
- Согласованность с интерфейсом проверяется передачей реального результата существующего общего Сравнения в Telegram-проекцию. Отдельные ожидаемые результаты второго diff-алгоритма не создаются.
- Чистые тесты покрывают одиночное добавление, одиночное удаление, разложение замены, смешанные изменения, несколько строк и Целевых областей и стабильный порядок.
- Форматирующие тесты покрывают пустые секции, Markdown-символы, HTML-подобный текст, CRLF/CR/LF, TAB, управляющие символы, пробельные фрагменты и многострочные bullets.
- Бюджетные тесты покрывают одну секцию на 300 символов, две секции по 150, передачу остатка, сокращение последнего фрагмента, единственный маркер неполноты и границу с emoji/astral Unicode.
- Отдельные тесты покрывают полное структурное Изменение без текста, неполное Сравнение с текстом и неполное Сравнение без доказанного текстового результата.
- Интеграционные тесты dispatcher покрывают получение пары по идентификатору Проверки после commit, подробный captured payload, сохранение URL, отсутствие прежней общей обрезки 3000 и неизменность строгой UTF-8 передачи.
- Fallback-тесты моделируют отсутствующую пару, повреждённый Снимок, ошибку форматирования и выбрасывающий fake logger. Во всех случаях базовая форма доходит до успешного fake sender и доставка отмечается как успешная.
- Logger-тест проверяет стабильное имя события и допустимые метаданные и доказывает отсутствие Снимков, URL, фрагментов, полного diff и готового сообщения.
- Регрессионные тесты подтверждают неизменность контрольного Уведомления, Окончательной ошибки, недоступной доставки, abandoned после рестарта, URL redaction, диагностики и exit-code mapping.
- Существующие тесты application-слоя продолжают доказывать отсутствие change-Уведомления для Базового снимка и результата без Изменений при выключенном режиме. Включённый режим контрольных Уведомлений проверяется отдельно и не считается change-details.
- HTTP и UI не получают новых контрактных тестов, поскольку их наблюдаемое поведение не меняется. Пользовательское руководство Telegram обновляется и остаётся согласованным с фактическим поведением.
- Приёмка требует чистого `typecheck`, полного набора тестов Website Change Monitor и полного набора тестов установленного контракта `telegram-alert-bus`.

## Out of Scope

- Размещение приложения в интернете, VPS, облачный хостинг, Tailscale и другие способы удалённого доступа.
- Перенос мониторинга с локального компьютера.
- Изменение desktop- или mobile-интерфейса приложения.
- Изменение локального двухколоночного Сравнения или создание вертикального diff.
- Новые страницы, маршруты, HTTP-операции и query-параметры.
- Изменение центра Уведомлений и browser notifications.
- Скриншоты, изображения, PDF, HTML и другие вложения.
- Использование Markdown или HTML как режима форматирования Telegram.
- Предметно-ориентированная логика для вакансий, товаров, новостей или других типов страниц.
- Отдельная логика для конкретных сайтов.
- Внешняя LLM для пересказа Изменений.
- Семантическое сопоставление старого и нового текста и отдельная секция «Изменено».
- Считать изменение `href` Изменением при неизменном видимом тексте.
- Изменение расписания Проверок, создания или хранения Снимков.
- Новая очередь Telegram, изменение retry-модели или доставка старых сообщений задним числом.
- Изменение или новая версия `telegram-alert-bus`.
- Реализация в рамках `/to-spec`; следующая стадия — `/to-tickets`.

### Acceptance Criteria

- Telegram-уведомление об Изменении показывает добавленный и/или удалённый текст.
- Замена всегда представлена как удаление плюс добавление; отдельной секции «Изменено» нет.
- Классификация соответствует существующему backend-Сравнению.
- Пустые секции не выводятся.
- Историческое имя страницы и безопасная исходная ссылка сохраняются.
- Подробности не превышают 300 Unicode code points и следуют правилу 150/150 с передачей остатка.
- При сокращении или неполном Сравнении выводится единственный явный маркер неполноты.
- Структурное Изменение без видимого текста получает согласованное пояснение только при полном Сравнении.
- Специальные символы, HTML-подобный текст, переносы строк и Unicode не ломают сообщение.
- Ошибка подготовки Подробностей записывается безопасно и не блокирует базовое Уведомление.
- Ошибка logger не блокирует базовое Уведомление.
- Контрольные Уведомления, Окончательные ошибки, UI, HTTP-контракт, расписание и хранение Снимков сохраняют прежнее поведение.
- Изменения покрыты автоматизированными тестами, а полный проверочный набор проходит.
