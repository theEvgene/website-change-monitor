# Выбрать общий поток данных и внутреннюю проекцию Изменений

## Question

Как, опираясь на существующее Сравнение, представить для Telegram упорядоченные добавления, удаления, надёжные замены, структурное Изменение без текстового diff и признак неполноты так, чтобы не менять UI, не создавать вторую diff-логику и не добавлять лишний архитектурный слой? Следует также выбрать минимальный runtime-контракт доступа к паре Снимков по `checkId` и шов передачи существующего `NdjsonLogger` к Telegram-доставке без миграции хранилища.

## Answer

Для MVP отдельная категория замен не нужна. По решению пользователя любые `replace`-строки существующего Сравнения проецируются как одна удалённая и одна добавленная строка. Это проще, не создаёт ложной семантической связи и не требует менять алгоритм Сравнения.

### Внутренняя проекция

Добавить одну чистую функцию в Telegram-модуль, например:

```ts
interface TelegramChangeDetails {
  removed: string[];
  added: string[];
  hasStructuralChanges: boolean;
  complete: boolean;
}

function projectTelegramChangeDetails(
  comparison: SnapshotComparison,
): TelegramChangeDetails;
```

Она обходит `targets` и их `text` в существующем порядке:

- `equal` игнорируется;
- `delete.before` добавляется в `removed`;
- `insert.after` добавляется в `added`;
- `replace.before` добавляется в `removed`, а `replace.after` — в `added`;
- `omitted` не создаёт фрагмент, а неполнота берётся из `comparison.complete`;
- `hasStructuralChanges` устанавливается по неравным строкам `structure`, а не только по `TargetComparison.kind`, потому что сам target может быть заменён из-за изменения текста.

Порядок внутри `removed` и `added` сохраняет порядок Целевых областей и строк Сравнения. Проекция не выполняет trim, дедупликацию, дополнительное сопоставление или собственный diff; очистка и бюджет относятся к форматтеру следующего билета.

Сообщение о структурном Изменении без видимого текста допустимо только когда `complete === true`, оба текстовых массива пусты и `hasStructuralChanges === true`. При `complete === false` отсутствие текстовых фрагментов не доказывает отсутствие текстовых изменений, поэтому форматтер не должен использовать формулировку «изменений видимого текста не обнаружено».

Эта функция образует один небольшой, но полезный интерфейс между общим `compareSnapshots` и Telegram-форматированием. Выделять общий новый слой или менять HTTP-контракт Сравнения не нужно. Термин закреплён в `CONTEXT.md` как «Подробности Изменения».

### Runtime-поток

1. Расширить `TelegramDeliveryJob` полем `checkId` и выбрать `e.check_id` в существующем `claimTelegramDelivery`.
2. Только для `kind === "change_detected"` dispatcher вызывает уже существующий `store.getComparison(job.checkId)`.
3. Полученная пара передаётся в существующий `compareSnapshots`, затем в `projectTelegramChangeDetails`.
4. Следующий форматтер добавляет Подробности Изменения к неизменяемому базовому сообщению. Для остальных видов Уведомлений путь не меняется.

Новая колонка, миграция, сохранение проекции или новый метод `MonitorStore` не нужны. Вычисление выполняется после commit, поэтому не удлиняет транзакцию завершения Проверки и при рестарте использует долговечные Снимки.

### Логирование fallback

Существующий `NdjsonLogger` следует передать как зависимость по цепочке CLI → `startApplication` → `buildHttpServer` → `createTelegramDispatcher`. Это реальный runtime-шов, а не новая система логирования. Ошибка чтения пары, Сравнения, проекции или форматирования перехватывается внутри dispatcher, записывается ограниченным событием вроде `telegram_change_details_failed` с `eventId`, `checkId`, стадией и безопасной ошибкой, после чего отправляется текущий базовый payload.

В технический журнал не передаются канонические Снимки, массивы `removed`/`added` или готовый полный текст сообщения. Ошибка Подробностей Изменения не меняет Результат проверки и не помечает доставку неуспешной, если базовый payload был доставлен.

ADR не требуется: решение локально, обратимо и следует существующим швам.
