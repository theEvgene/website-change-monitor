# Определить формат сообщения, бюджет, сокращение и fallback

## Question

Как детерминированно форматировать plain-text Telegram-уведомление с отдельными секциями только для удалённого и добавленного текста, сохранять порядок и непустые секции, обрабатывать переносы и специальные символы, ограничивать или разбивать большой diff с явной отметкой неполноты и гарантировать отправку базового уведомления при любой ошибке расширенного форматирования? Следует учесть существующий multipart-механизм `telegram-alert-bus` и определить безопасное ограниченное событие `NdjsonLogger`, не содержащее сырого Снимка или полного diff.

## Answer

Для MVP Telegram получает одно компактное логическое уведомление. Подробности Изменения имеют общий бюджет 300 Unicode code points; специально заполнять лимит Telegram или отправлять большой diff несколькими частями не требуется. Внешний multipart-механизм `telegram-alert-bus` остаётся страховкой для необычно длинной базовой части или URL, но не используется как стратегия показа Подробностей.

### Логическая структура

```text
Обнаружено изменение

Страница: {историческое имя Монитора}

➕ Добавлено:
• {фрагмент}

➖ Удалено:
• {фрагмент}

…показана только часть изменений

Ссылка: {безопасный исторический URL}
```

- Секция «Добавлено» идёт первой, «Удалено» — второй.
- Пустая секция полностью исключается вместе с заголовком.
- Базовая идентификация страницы и ссылка выводятся всегда и не входят в 300-символьный бюджет.
- Текущий `job.title` остаётся источником первой строки. Для успешной подробной формы дублирующее текущее `job.body` не требуется; fallback использует его без изменений.
- Сообщение остаётся plain text. Markdown/HTML escaping и `parse_mode` не добавляются, поэтому Markdown-символы и HTML-подобный текст показываются буквально.

### Нормализация фрагментов

Перед применением бюджета каждый фрагмент:

1. нормализуется в NFC;
2. переводит CRLF/CR в LF;
3. заменяет управляющие C0/DEL-символы, кроме LF и TAB, пробелом;
4. обрезает внешние пробельные символы;
5. исключается, если после этого пуст.

Внутренние переносы сохраняются; продолжение многострочного фрагмента выводится с отступом, чтобы оно оставалось частью одного bullet. Пробелы внутри текста дополнительно не схлопываются и предметно-ориентированная очистка не выполняется.

### Детерминированный бюджет

Бюджет считается по Unicode code points только в отображаемом тексте фрагментов, без заголовков, bullet-префиксов, пустых строк и маркера неполноты.

- Если непуста только одна секция, она получает все 300 символов.
- Если непусты обе, каждая сначала получает 150 символов.
- Если одной секции требуется меньше 150, её неиспользованный остаток передаётся другой.
- Внутри секции фрагменты берутся в порядке проекции.
- Полностью помещающиеся фрагменты сохраняются целиком. Последний непомещающийся фрагмент обрезается по code points до остатка бюджета; последующие фрагменты не выводятся.

Маркер `…показана только часть изменений` выводится ровно один раз, если:

- хотя бы один нормализованный текстовый символ не поместился в бюджет; или
- `SnapshotComparison.complete === false`, даже если подготовленные фрагменты формально поместились.

При полном Сравнении, пустых текстовых секциях и наличии структурных Изменений выводится согласованное пояснение: `Изменилась структура отслеживаемой области. Изменений видимого текста не обнаружено.` Оно не считается Подробностями и не расходует 300-символьный бюджет.

Если Сравнение неполно и текстовые секции пусты, указанное пояснение использовать нельзя: система отправляет базовое уведомление и маркер неполноты, поскольку отсутствие видимого текстового изменения не доказано.

### Размер полного payload

Удалить прежнюю безусловную обрезку всего `message` до 3000 code points: она может отрезать ссылку и скрывает уже существующее разбиение sender. При обычных ограниченных Подробностях сообщение останется существенно меньше лимита Telegram. Если базовая часть или URL всё же сделают его длиннее, `telegram-alert-bus` валидирует payload до 100 000 characters и безопасно разделит его на сообщения до 4096 characters с `[N/M]`.

### Fallback и журнал

Формирование расширенной формы изолируется от базового payload:

1. Сначала детерминированно строится текущая базовая форма: `job.title`, безопасный URL и `job.body`.
2. Для `change_detected` dispatcher пытается загрузить пару Снимков, выполнить общее Сравнение, проекцию и подробное форматирование.
3. Любое отсутствие пары или исключение на этих стадиях перехватывается.
4. Dispatcher best-effort пишет `telegram_change_details_failed` через переданный `NdjsonLogger`.
5. В sender передаётся заранее подготовленная базовая форма; её успешная доставка остаётся `delivered`.

Событие журнала содержит только `eventId`, `checkId`, одну из стабильных стадий `load_comparison | compare | project | format`, имя ошибки и безопасное ограниченное сообщение ошибки. Канонические Снимки, фрагменты, полный diff, готовый Telegram-текст и URL в журнал не передаются. Ошибка самого logger также перехватывается и не блокирует базовое Уведомление.

Для `check_failed_final` и `control_check_ok` подробная ветка не запускается, поэтому их формат и поведение сохраняются.

Новый термин предметной области и ADR не требуются: бюджет и fallback являются локальными, обратимыми правилами представления существующих Подробностей Изменения.
