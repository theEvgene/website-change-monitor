# Проверить реализационные швы и полный набор автоматизированных тестов

## Question

Какие существующие интерфейсы, типы, компоненты и тестовые инструменты потребуется изменить, как покрыть минимальные сценарии, 300-символьный бюджет Подробностей, структурное Изменение, неполное Сравнение и fallback-логирование, и достаточно ли принятых решений для implementation-ready спецификации без скрытых продуктовых или архитектурных вопросов?

## Answer

Полная матрица изменений и тестов зафиксирована в [проверке готовности реализации](../research/05-implementation-readiness.md).

Фича реализуема внутри существующего Telegram-пути: новый чистый модуль проекции/форматирования, `checkId` в runtime job, вызов существующего `compareSnapshots` перед доставкой и передача существующего `NdjsonLogger` в dispatcher. Миграция, новый HTTP-контракт, UI-изменения, новая зависимость и изменения `telegram-alert-bus` не нужны.

Все исходные сценарии сопоставлены с автоматизированными тестами, включая упрощённое правило `replace → removed + added`, 300-символьный бюджет, специальные символы, структурное и неполное Сравнение, fallback и согласованность с UI diff. Базовые проверки прошли: TypeScript typecheck, 157 Node-тестов при одном skipped и 32 теста sender.

Открытых продуктовых или архитектурных вопросов не осталось. Карта готова к `/to-spec`.
