# Существующее Сравнение и семантика текстовых Изменений

## Источник решения об Изменении

- Проверка формирует нормализованный Снимок в `src/server/application/monitor-service.ts`.
- `sameSnapshotContent(beforeJson, afterJson)` из `src/server/application/snapshot-comparison.ts` определяет, есть ли Изменение. Сравниваются упорядоченные Целевые области, их структура `elements` и `visibleText`.
- Метаданные ссылок исключены из этого решения: изменение только `href` не создаёт Изменение.
- Если содержимое различается, `completeChange` атомарно сохраняет новый Снимок, связывает Проверку с прежним и новым Снимками и создаёт Уведомление. Само подробное Сравнение в этот момент пока не вычисляется.

## Формирование Сравнения

Единственная реализация находится в `src/server/application/snapshot-comparison.ts`:

```text
compareSnapshots(beforeCanonicalJson, afterCanonicalJson)
  -> SnapshotComparison { complete, targets[] }
  -> TargetComparison { kind, structure[], text[] }
  -> TextDiffRow / DiffRow
```

- Поддерживается `formatVersion: 1`; неизвестная версия или повреждённый Снимок завершаются ошибкой.
- Целевые области сначала сопоставляются тем же детерминированным построчным алгоритмом по их сериализованному содержимому.
- Для сопоставленной пары отдельно формируются:
  - `structure`: строки preorder-представления элементов;
  - `text`: строки `visibleText`, разделённые по `\n`, с безопасными ссылочными диапазонами на каждой стороне.
- Текст и Целевые области сохраняют порядок, полученный из Снимков и алгоритма Myers.

## Гарантии и ограничения `DiffRow`

| `kind` | Гарантия |
| --- | --- |
| `equal` | Строки на обеих сторонах совпадают точно. |
| `delete` | Старая строка присутствует только слева. |
| `insert` | Новая строка присутствует только справа. |
| `replace` | Удалённая и добавленная строки находятся на одинаковой позиции внутри одного непрерывного diff-hunk и попарно сопоставлены по порядку. |
| `omitted` | Алгоритм превысил бюджет; строка содержит точные количества непоказанных строк слева и справа, а `SnapshotComparison.complete` становится `false`. |

Важное ограничение: `replace` детерминирован, но не является семантической проверкой сходства. `pairHunks` попарно соединяет удаления и вставки одного hunk по порядковому номеру. Поэтому любой `replace` согласован с UI, но не обязательно достаточно надёжен для пользовательского утверждения «этот старый смысл заменён именно этим новым». Билет «Выбрать общий поток данных и внутреннюю проекцию Изменений» должен определить консервативное правило: принять UI-пару или понижать сомнительную пару до отдельных «Удалено» и «Добавлено», не выполняя нового diff.

Ограничители Сравнения:

- более 20 000 строк в одной секции сразу переводят её в bounded-режим;
- более 5 000 000 переходов Myers также переводят её в bounded-режим;
- bounded-режим сохраняет до 50 точных общих строк в начале и конце и добавляет `omitted`;
- на уровне Целевых областей пропущенные элементы не создают `TargetComparison`, но `complete: false` честно сигнализирует о неполноте.

## Передача во frontend

Поток уже полностью backend-driven:

1. `MonitorStore.getComparison(checkId)` в `src/server/persistence/monitor-store.ts` получает два связанных канонических Снимка.
2. `MonitorService.getComparison(checkId)` вызывает `compareSnapshots`.
3. `GET /api/checks/{checkId}/comparison` в `src/server/http/server.ts` возвращает результат по схеме `ComparisonResponseV1` из `src/server/http/contract.ts`.
4. `loadComparison` в `src/ui/ComparisonModal.tsx` загружает этот JSON.
5. Модальное окно показывает `targets.flatMap(target => target.text)`, включая неизменённые строки, и отдельно предупреждает при `complete: false`. `structure` в текущем UI не отображается.

Frontend не вычисляет и не классифицирует diff самостоятельно.

## Минимальный общий backend-контракт

Новый общий diff-модуль не нужен. Существующий глубокий модуль уже имеет подходящий интерфейс:

```ts
compareSnapshots(beforeCanonicalJson: string, afterCanonicalJson: string): SnapshotComparison
```

Рекомендуемый шов для дальнейшего проектирования:

- и HTTP-представление, и Telegram используют один `SnapshotComparison`, сформированный этой функцией;
- Telegram-специфичная логика является только чистой проекцией `SnapshotComparison` в добавления, удаления, допустимые замены и признак неполноты;
- проекция не повторяет Myers, не сравнивает исходные строки заново и не импортирует frontend-типы;
- способ получения пары Снимков и момент вычисления определяются после исследования текущей Telegram-доставки.

Такой шов обеспечивает единообразие классификации с UI и оставляет форматирование Telegram отдельной задачей представления.

## Подтверждённые сценарии

- Изменение только структуры создаёт Изменение, но все текстовые строки могут остаться `equal`; применяется уже согласованное структурное пояснение.
- Изменение только ссылки не создаёт Изменение.
- `insert` и `delete` можно прямо отображать как «Добавлено» и «Удалено».
- `replace` требует консервативного решения в следующем проектном билете.
- `omitted` и `complete: false` обязательно должны переходить в признак неполного Telegram-представления.
