# Готовность реализации подробных Telegram-уведомлений

## Вердикт

Карта готова к `/to-spec`. Все продуктовые и архитектурные решения приняты, `Not yet specified` пуст, а реализация укладывается в существующие швы без изменения UI, HTTP-контракта, схемы SQLite или внешнего `telegram-alert-bus`.

## Затрагиваемые файлы и интерфейсы

### Основная реализация

| Файл | Изменение |
| --- | --- |
| `src/server/notifications/telegram-change-details.ts` | Новый чистый модуль: тип `TelegramChangeDetails`, проекция из `SnapshotComparison`, нормализация, распределение бюджета и plain-text форматирование |
| `src/server/persistence/monitor-store.ts` | Добавить `checkId` в `TelegramDeliveryJob` и выбрать `e.check_id` в `claimTelegramDelivery`; таблицы не менять |
| `src/server/notifications/telegram-dispatcher.ts` | Сначала строить базовый payload; для `change_detected` получать пару, вызывать `compareSnapshots`, проекцию и форматтер; при ошибке логировать и отправлять базовую форму; удалить обрезку всего `message` до 3000 |
| `src/server/http/server.ts` | Передать существующий `NdjsonLogger` dispatcher |
| `src/server/operations/start.ts` | Принять logger как runtime-зависимость и передать `buildHttpServer` |
| `src/server/cli.ts` | Создать logger до `startApplication`, а не после успешного запуска, и использовать тот же экземпляр для lifecycle и Telegram fallback |
| `docs/http-api.md` | Описать Telegram-only Подробности Изменения, секции, бюджет 300, маркер неполноты и базовый fallback |

`src/server/application/snapshot-comparison.ts` остаётся единственным алгоритмом diff. Менять его типы или HTTP-схему Сравнения не требуется. Существующий `MonitorStore.getComparison(checkId)` уже предоставляет нужную пару Снимков.

Logger следует передавать как существующий `NdjsonLogger`, без нового logging-интерфейса или адаптера. В прямых тестовых вызовах `buildHttpServer`, `startApplication` и `createTelegramDispatcher` используется небольшой fake `NdjsonLogger`.

### Что не меняется

- миграции и schema version;
- `notification_events` и `notification_deliveries`;
- REST/SSE/OpenAPI;
- React UI и центр Уведомлений;
- расписание, получение страницы и сохранение Снимков;
- форматы окончательной ошибки и контрольного Уведомления;
- зависимости `package.json`;
- репозиторий `telegram-alert-bus`.

## Последовательность реализации

1. Добавить `checkId` в долговечный путь claim без изменения схемы.
2. Реализовать и полностью протестировать чистый модуль Подробностей Изменения.
3. Подключить модуль в dispatcher поверх существующего `compareSnapshots`.
4. Провести logger от CLI к dispatcher и проверить базовый fallback, включая ошибку самого logger.
5. Обновить пользовательскую документацию и прогнать все проверки.

Такой порядок даёт вертикальный tracer: после шага 3 настоящее change-событие уже проходит от сохранённых Снимков до captured sender payload, а шаг 4 завершает отказоустойчивость.

## Автоматизированные тесты

### Новый `tests/telegram-change-details.test.ts`

Тестировать через публичные чистые функции модуля, не через его внутренние helpers:

| Сценарий | Наблюдаемый результат |
| --- | --- |
| Одна вставка | Только «Добавлено», исходный текст сохранён |
| Одно удаление | Только «Удалено», исходный текст сохранён |
| Одна `replace`-строка | Старый текст в «Удалено», новый в «Добавлено»; секции «Изменено» нет |
| Вставки, удаления и `replace` вместе | Обе секции содержат ожидаемые фрагменты в порядке `targets`/rows |
| Несколько строк и Целевых областей | Порядок внутри каждой секции стабилен |
| Markdown-символы | Выводятся буквально |
| HTML-подобный текст | Выводится буквально |
| CRLF, CR, LF, TAB и управляющие символы | Применяется согласованная нормализация, многострочный bullet сохраняет принадлежность |
| Обе секции больше бюджета | По 150 code points и один маркер неполноты |
| Одна секция короткая | Неиспользованный бюджет передан другой |
| Только одна секция | Она получает все 300 code points |
| Emoji/astral Unicode на границе | Суррогатная пара не разрезается |
| Пустые/пробельные фрагменты | Пустые секции не выводятся |
| `complete: false` | Маркер неполноты присутствует независимо от фактического расхода бюджета |
| Полное структурное Изменение без текста | Выводится согласованное структурное пояснение |
| Неполное Сравнение без текстовых строк | Структурное пояснение не выводится; остаются базовая форма и маркер |
| Согласованность с UI | В функцию передаётся реальный результат `compareSnapshots`; полученные added/removed точно соответствуют его неравным `text`-строкам |

### Расширение `tests/telegram-dispatcher.test.ts`

- captured payload настоящего change-события содержит имя, URL и ожидаемые добавления/удаления;
- `TelegramDeliveryJob.checkId` ведёт к сохранённой паре после commit;
- сообщение больше не обрезается безусловно до 3000;
- повреждённый или отсутствующий Снимок приводит к текущему базовому сообщению, `delivered` при успехе sender и одному безопасному событию logger;
- logger получает только IDs, stage и ограниченную ошибку, без URL/Снимка/diff/message;
- исключение fake logger не блокирует базовую доставку;
- окончательная ошибка и контрольное Уведомление сохраняют прежний payload;
- URL credentials по-прежнему удаляются, monitor ID и диагностика остаются ограниченными.

### Существующие интеграционные тесты

- `tests/monitor-service.test.ts`: change/no-change, атомарность и отсутствие уведомления при Базовом снимке;
- `tests/control-notifications.test.ts`: режим контрольных Уведомлений не смешивается с change-details;
- `tests/snapshot-comparison.test.ts`: единый diff, `replace`, `omitted`, structure/text и links;
- `tests/start.test.ts` и при необходимости `tests/cli.test.ts`: один logger передан по runtime-цепочке;
- `tests/http-guide.test.ts`: документационные команды остаются валидными; новой HTTP-операции нет.

Минимальный сценарий «изменений нет — уведомление не отправляется» проверяется при выключенном режиме контрольных Уведомлений; при включённом режиме существующее `control_check_ok` остаётся отдельным, неизменённым поведением.

```powershell

```

```powershell

```

- TypeScript typecheck прошёл;

- полный `telegram-alert-bus`: 32 passed.

Первый полный Vitest-прогон дополнительно сообщил необработанный Playwright `download.cancel` после закрытия browser context. Изолированный `playwright-page-probe.test.ts` (26 passed) и повторный полный прогон прошли.
