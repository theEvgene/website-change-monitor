# Управление Telegram-уведомлениями в текущем запуске

Status: ready-for-agent

## Problem Statement

Website Change Monitor всегда пытается направлять созданные Уведомления в
Telegram. Пользователь не может временно отказаться от этого канала, не меняя
конфигурацию внешнего sender. Недоступный Telegram при этом переводит состояние
работающего приложения в warning даже тогда, когда пользователь сознательно не
хочет получать Telegram-сообщения.

Существующий Режим контрольных уведомлений управляет сообщениями о Проверках без
Изменений, но не выражает главный выбор: использовать ли Telegram вообще. Если
просто добавить независимый переключатель, могут возникнуть противоречивые
состояния, например включённые контрольные Telegram-уведомления при выключенном
канале, ошибочная подпись «Не отправлено» для намеренно пропущенной доставки,
повторная отправка старых сообщений после включения или ложное предупреждение о
состоянии системы.

Нужно дать пользователю ясное управление Telegram в рамках текущего запуска,
сохранив Проверки, внутренние и браузерные Уведомления, исторические результаты
доставки и независимую диагностику `doctor`.

## Solution

Добавить в существующую модалку настроек главный переключатель «Отправлять
уведомления в Telegram». Он управляет всеми Telegram-сообщениями: об Изменениях,
Окончательных ошибках и Проверках без Изменений. Существующий переключатель
«Уведомлять при отсутствии изменений» становится зависимым: он доступен только
при включённом главном переключателе и автоматически выключается вместе с ним.

Обе настройки действуют только в текущем процессе. Каждый новый запуск начинает
с включённых Telegram-уведомлений и выключенных уведомлений при отсутствии
Изменений. SQLite не восстанавливает эти значения.

Новые и ещё ожидающие Telegram-доставки при выключении получают нейтральное
состояние «Telegram отключён». Уже начатая отправка завершается, а завершённые
исторические результаты не переписываются. После повторного включения старые
пропущенные Уведомления не досылаются; доступность Telegram немедленно
перепроверяется, и только новые ожидающие доставки используют результат этой
проверки.

Выключенный Telegram не ухудшает состояние работающего приложения. Верхняя
плашка остаётся зелёной «Система готова», а карточка Telegram в модалке состояния
становится серой и сообщает: «Уведомления через Telegram отключены в
настройках.». Отдельный процесс `doctor` продолжает всегда проверять Telegram.

## User Stories

1. As a пользователь, I want to выключить все Telegram-уведомления одним переключателем so that приложение временно не отправляет мне сообщения в Telegram.
2. As a пользователь, I want to продолжать выполнять Проверки при выключенном Telegram so that управление каналом не останавливает мониторинг страниц.
3. As a пользователь, I want to продолжать получать внутренние и браузерные Уведомления so that выключение одного канала не отключает остальные.
4. As a пользователь, I want to выключить Telegram-сообщения об Изменениях so that новые обнаруженные Изменения не направляются в этот канал.
5. As a пользователь, I want to выключить Telegram-сообщения об Окончательных ошибках so that режим Telegram применяется ко всем видам сообщений согласованно.
6. As a пользователь, I want to выключить Telegram-сообщения о Проверках без Изменений so that зависимая настройка не обходит главный переключатель.
7. As a пользователь, I want to видеть главный переключатель с названием «Отправлять уведомления в Telegram» so that его назначение однозначно.
8. As a пользователь, I want to видеть рядом существующий переключатель «Уведомлять при отсутствии изменений» so that связанные настройки находятся в одном месте.
9. As a пользователь, I want to не иметь возможности включить уведомления об отсутствии Изменений при выключенном Telegram so that интерфейс не допускает противоречивую конфигурацию.
10. As a пользователь, I want to автоматически выключать уведомления об отсутствии Изменений вместе с Telegram so that мне не приходится выключать зависимый режим отдельно.
11. As a пользователь, I want to не восстанавливать прежнее значение зависимого переключателя при повторном включении Telegram so that контрольные сообщения включаются только явным действием.
12. As a пользователь, I want to иметь возможность включить уведомления об отсутствии Изменений при включённом, но временно недоступном Telegram so that настройка выражает моё намерение, а не текущую доступность sender.
13. As a пользователь, I want to начинать каждый новый запуск с включённым Telegram so that стандартное поведение приложения остаётся прежним.
14. As a пользователь, I want to начинать каждый новый запуск с выключенными уведомлениями при отсутствии Изменений so that контрольные сообщения остаются явной опцией.
15. As a пользователь, I want to не переносить значения этих переключателей между процессами so that временное отключение не становится незаметной постоянной настройкой.
16. As a пользователь, I want to видеть «Telegram отключён» возле Уведомления, намеренно не направленного в Telegram, so that это состояние не выглядит ошибкой доставки.
17. As a пользователь, I want to видеть одинаковую нейтральную подпись в Журнале, Истории Монитора и центре Уведомлений so that разные разделы не противоречат друг другу.
18. As a пользователь, I want to не видеть причину ошибки рядом с намеренно отключённой доставкой so that добровольный выбор не воспринимается как неисправность.
19. As a пользователь, I want to завершить Telegram-отправку, уже начатую до выключения so that результат фактически запущенной операции не искажается.
20. As a пользователь, I want to остановить ещё не начатые отправки текущего запуска so that после выключения sender не получает новые работы.
21. As a пользователь, I want to сохранить завершённые исторические состояния доставки so that переключение настройки не переписывает факты прошлого.
22. As a пользователь, I want to не получать пропущенные сообщения задним числом после включения Telegram so that повторное включение не создаёт поток устаревших Уведомлений.
23. As a пользователь, I want to немедленно перепроверить Telegram при его включении so that новые доставки используют актуальное состояние канала.
24. As a пользователь, I want to удерживать новые доставки во время перепроверки so that sender не используется до подтверждения доступности.
25. As a пользователь, I want to видеть нейтральное состояние проверки доступности so that краткий переход не выглядит подтверждённой ошибкой.
26. As a пользователь, I want to получить warning, если включённый Telegram недоступен, so that неисправность ожидаемого канала остаётся заметной.
27. As a пользователь, I want to видеть зелёную плашку «Система готова» при выключенном Telegram so that намеренно исключённый канал не ухудшает состояние приложения.
28. As a пользователь, I want to видеть серую карточку «Telegram отключён» в состоянии системы so that отключённый канал визуально отличается и от доступного, и от неисправного.
29. As a пользователь, I want to видеть подпись «Уведомления через Telegram отключены в настройках.» so that причина нейтрального состояния понятна.
30. As a пользователь, I want to не видеть кнопку повторной проверки Telegram при выключенном канале so that интерфейс не предлагает действие, противоречащее настройке.
31. As a пользователь, I want to не видеть действие перехода в настройки из серой карточки so that модалка состояния остаётся компактной.
32. As a пользователь, I want to сохранить текущую зелёную карточку доступного Telegram so that привычное положительное состояние не меняется.
33. As a пользователь, I want to сохранить warning, причину и ручную перепроверку для включённого, но недоступного Telegram so that существующая диагностика остаётся полезной.
34. As a пользователь, I want to видеть подтверждённые сервером значения переключателей so that ошибка HTTP не оставляет интерфейс в ложном состоянии.
35. As a пользователь, I want to видеть ошибку изменения настройки в существующем toast so that возле переключателей не появляется лишний технический текст.
36. As a пользователь, I want to не иметь возможности повторно нажимать переключатели во время изменения и перепроверки so that конкурирующие действия не создаются случайно.
37. As an агент автоматизации, I want to читать и изменять обе настройки через существующий локальный HTTP-интерфейс so that UI и автоматизация используют один контракт.
38. As an агент автоматизации, I want to продолжать отправлять прежний update только с `notifyWhenUnchanged` so that расширение контракта не ломает существующие вызовы.
39. As an агент автоматизации, I want to получать нормализованное effective-состояние so that противоречивый запрос не оставляет сервер в невозможной комбинации.
40. As a пользователь, I want to выключить Telegram во время незавершённой перепроверки so that последнее моё действие всегда имеет приоритет.
41. As a пользователь, I want to не позволить позднему результату перепроверки скрыто включить Telegram so that состояние соответствует последней команде.
42. As a владелец приложения, I want to продолжать проверять Telegram командой `doctor` независимо от временной настройки работающего процесса so that диагностика следующего запуска остаётся полной.
43. As a пользователь, I want to сохранить расписание Проверок, Снимки и Историю Мониторов so that новая настройка влияет только на направление Уведомлений.
44. As a пользователь, I want to сохранить существующее поведение центра Уведомлений so that Telegram не становится владельцем внутренних событий.

## Implementation Decisions

- Единственным владельцем обеих настроек становится server-scoped runtime-модуль
  Уведомлений, создаваемый на срок жизни HTTP-сервера.
- Начальное состояние runtime-модуля при каждом запуске: Режим
  Telegram-уведомлений включён, Режим контрольных уведомлений выключен.
- React является только представлением серверного состояния. SQLite и Telegram
  dispatcher не владеют пользовательскими настройками.
- Существующие persisted-данные `notify_when_unchanged` перестают читаться и
  изменяться. Таблица остаётся как безопасные legacy-данные; обратная миграция
  не создаётся.
- Runtime-модуль имеет фазы `checking`, `enabled` и `disabled`. Generation token
  не позволяет позднему async-результату перепроверки отменить более новую
  команду пользователя.
- Существующие операции чтения и изменения настроек сохраняются. Ответ чтения и
  успешного изменения содержит `telegramEnabled`, `notifyWhenUnchanged` и
  `telegramPhase`.
- Update принимает непустой частичный набор двух boolean-полей. Неизвестные
  поля, пустой объект и неверные типы отклоняются существующей ошибкой
  некорректного запроса.
- Прежний update только с `notifyWhenUnchanged` остаётся совместимым.
- Если effective `telegramEnabled` равен `false`, effective
  `notifyWhenUnchanged` всегда равен `false`, а фаза равна `disabled`.
- Противоречивый запрос с выключенным Telegram и включёнными уведомлениями при
  отсутствии Изменений нормализуется к обоим выключенным значениям.
- Команда включения переводит runtime в `checking`, немедленно запускает
  перепроверку sender и возвращает актуальное effective-состояние после
  применения результата либо более новой команды.
- Во время `checking` новые Telegram-доставки создаются ожидающими, но dispatcher
  не может получить их в работу.
- Dispatcher проверяет runtime-gate перед каждым получением следующей доставки,
  а не только перед началом цикла.
- Снимок notification policy снимается непосредственно перед commit Проверки и
  передаётся в транзакцию хранения.
- Изменение и Окончательная ошибка всегда создают внутреннее Уведомление.
  Runtime policy определяет только начальное Состояние доставки Telegram.
- Уведомление о Проверке без Изменений создаётся только при включённом Режиме
  контрольных уведомлений. Оно по-прежнему доступно через Telegram и браузер,
  но не добавляется в центр Уведомлений.
- Каждое созданное событие сохраняет одну строку Telegram-доставки. Отсутствие
  строки не используется для обозначения отключённого канала.
- Добавляется терминальное долговечное состояние `disabled`. Оно означает
  намеренно пропущенную доставку без будущей повторной отправки.
- Для `disabled` причина ошибки и diagnostic всегда отсутствуют.
- Нужна следующая migration SQLite, расширяющая ограничение допустимых состояний
  доставки значением `disabled`. Она пересоздаёт таблицу, дословно сохраняет
  старые строки и восстанавливает индекс; backfill не выполняется.
- Выключение в одной транзакции переводит только ожидающие доставки текущего
  процесса в `disabled`. Уже отправляемые, завершённые и принадлежащие другим
  процессам строки не меняются.
- Получение работы dispatcher остаётся ограниченным состоянием `pending`;
  `disabled` никогда не выдаётся sender и не возвращается в `pending`.
- Startup и shutdown продолжают переводить только незавершённые
  `pending`/`sending` прежней сессии в существующее состояние `abandoned`.
- Общий union runtime-состояния Telegram расширяется значениями `available`,
  `unavailable`, `checking` и `disabled`. Он используется Telegram-state и
  полем Telegram в health.
- Чтение Telegram-state не запускает перепроверку.
- Ручная перепроверка при выключенном Telegram не вызывает sender и
  идемпотентно возвращает `disabled`.
- Верхнеуровневый health остаётся `ready` при `available` и `disabled` и
  `degraded` при `checking` и `unavailable`.
- Presentation не приравнивает `checking` к ошибке: верхняя плашка показывает
  нейтральное состояние загрузки до результата.
- Существующий SSE-механизм не меняется. Переход `pending` в `disabled`
  публикуется как обновление доставки; сразу созданный `disabled` приходит как
  обычное событие.
- Единый formatter Состояния доставки Telegram возвращает «Отправляется» для
  `pending`/`sending`, «Отправлено» для `delivered`, «Telegram отключён» для
  `disabled` и «Не отправлено» для остальных терминальных исходов.
- Модалка настроек получает два переключателя. Во время update оба недоступны;
  дочерний дополнительно недоступен при выключенном Telegram или фазе
  `checking`.
- После повторного включения зависимый переключатель остаётся выключенным. При
  завершённой проверке он доступен даже при `unavailable`, поскольку отражает
  пользовательское намерение, а не доступность sender.
- При ошибке изменения настройки UI сохраняет последнее подтверждённое состояние
  и использует существующий toast.
- При `disabled` верхняя плашка остаётся зелёной «Система готова». Tooltip не
  утверждает, что Telegram доступен.
- Карточка Telegram при `disabled` становится серой, показывает «Telegram
  отключён» и подпись «Уведомления через Telegram отключены в настройках.» без
  warning, причины ошибки, повторной проверки или перехода в настройки.
- `doctor` не получает runtime-модуль и продолжает напрямую проверять
  конфигурацию и доступность Telegram при каждом отдельном запуске.
- Новый ADR и новый внешний слой абстракции не требуются.

## Testing Decisions

- Главный сквозной тестовый шов — существующий локальный HTTP-интерфейс,
  построенный с временной настоящей SQLite и управляемым fake Telegram sender.
  Через него проверяются настройки, health и переходы без обращения к приватным
  полям runtime-модуля.
- Отдельные store/dispatcher-тесты используются для атомарных переходов и гонок,
  которые невозможно надёжно доказать только UI-тестом.
- UI-тесты проверяют доступное пользователю состояние двух переключателей,
  плашки, карточки, toast и общие подписи доставки, а не локальную структуру
  React state.
- Migration-тест создаёт базу предыдущей версии со всеми прежними состояниями,
  применяет новую migration и доказывает дословное сохранение идентификаторов,
  причин, diagnostics и временных меток.
- Migration-тест также доказывает, что `disabled` принимается, неизвестное
  состояние отклоняется и версия схемы обновляется.
- Новый сервер на новой и повторно открытой Базе данных всегда возвращает
  включённый Telegram и выключенные уведомления при отсутствии Изменений,
  независимо от legacy-значения SQLite.
- Контрактные тесты покрывают полное чтение настроек, старый частичный update,
  обновление каждого поля, нормализацию противоречивой комбинации и ошибки для
  пустого, неизвестного и неверно типизированного payload.
- Тест выключения доказывает переход только `pending` текущего процесса в
  `disabled`, отсутствие причины/diagnostic и неизменность `sending`,
  завершённых состояний и другого процесса.
- Тест гонки доказывает, что уже `sending` доставка завершается фактическим
  исходом, а следующая `pending` становится `disabled`.
- Тест dispatcher доказывает, что `disabled` никогда не получается в работу и
  не оживает после включения, перепроверки или drain.
- Тест включения доказывает удержание новых `pending` во время проверки,
  отправку только новых ожидающих доставок после успеха и перевод в
  `unavailable` после неуспеха.
- Тест generation доказывает, что выключение во время перепроверки побеждает, а
  поздний результат не меняет effective-состояние.
- Тест ручной перепроверки при `disabled` доказывает, что inspector не
  вызывается.
- Health-тесты покрывают четыре Telegram-state: `available` и `disabled` дают
  `ready`, `checking` и `unavailable` дают `degraded`.
- Event-тесты подтверждают, что Изменение и Окончательная ошибка сохраняют
  внутреннее событие с delivery `disabled`, не вызывая sender.
- Тесты Режима контрольных уведомлений подтверждают отсутствие события при
  выключенном дочернем режиме и создание browser/Telegram-события при обоих
  включённых режимах.
- SSE-тест подтверждает обновление `pending → disabled` и однократную доставку
  сразу созданного `disabled` события через существующие типы событий.
- Общий formatter и интеграционные UI-тесты доказывают подпись «Telegram
  отключён» без причины ошибки в Журнале, Истории Монитора и центре
  Уведомлений.
- UI-тест модалки настроек покрывает начальные значения, автоматическое
  выключение и блокировку дочернего переключателя, отсутствие восстановления,
  busy/checking и доступность при enabled+unavailable.
- UI-тест ошибки update доказывает сохранение подтверждённых значений и
  появление существующего error-toast без сообщения возле переключателя.
- UI-тест состояния системы покрывает зелёную плашку и серую карточку при
  `disabled`, точные тексты, отсутствие recheck/action, нейтральный loading при
  `checking`, warning при `unavailable` и ready при `available`.
- Тест фонового обновления доказывает, что poll не превращает `disabled` в
  warning и не отменяет более новую команду выключения.
- Существующие тесты закрытия модалок по backdrop сохраняются без изменения
  поведения.
- Существующие тесты `doctor` продолжают проверять Telegram напрямую и не
  зависят от runtime-настроек HTTP-сервера.
- Регрессионный набор сохраняет прежние результаты `delivered`, `unavailable`,
  `permanent`, `temporary`, `timeout`, `abandoned`, расписание Проверок,
  Снимки, Историю Мониторов и остальные каналы Уведомлений.
- Приёмка требует чистого typecheck, полного набора тестов Website Change
  Monitor и согласованного OpenAPI-контракта.

## Out of Scope

- Сохранение новых переключателей между процессами или чтение их значений из
  SQLite.
- Настройки Telegram на уровне отдельного Монитора.
- Повторная отправка старых `disabled`, `unavailable` или иных завершённых
  доставок после включения Telegram.
- Связывание `doctor` с временным состоянием работающего HTTP-сервера.
- Отключение проверки Telegram внутри `doctor`.
- Новые каналы Уведомлений.
- Изменение внешнего Telegram sender или его формата сообщений.
- Изменение содержания Telegram-сообщений.
- Изменение расписания Проверок, Подготовки страницы, Снимков, Сравнения или
  Истории Мониторов.
- Новый раздел настроек, новые страницы или переработка навигации.
- Переработка Журнала, Истории Монитора или центра Уведомлений за пределами
  нейтральной подписи доставки.
- Переход из карточки состояния системы в настройки.
- Реализация в рамках `/to-spec`; следующая стадия — `/to-tickets`.

## Further Notes

- Спецификация синтезирована из завершённой [Wayfinder-карты](map.md) и
  связанных с ней исследовательских билетов. Детальное обоснование жизненного
  цикла, модели delivery и HTTP/UI-контракта остаётся в связанных материалах
  карты и здесь не дублируется.
- Тестовые швы были последовательно согласованы в рамках Wayfinder: внешний
  HTTP-интерфейс является главным сквозным швом; store/dispatcher, migration,
  SSE и React используются как специализированные швы для собственных
  наблюдаемых гарантий.
- Спецификация не требует дополнительного интервью перед `/to-tickets`.

### Acceptance Criteria

- В настройках присутствуют оба согласованных переключателя.
- Выключение Telegram автоматически выключает и блокирует уведомления при
  отсутствии Изменений.
- Каждый новый процесс начинает с включённого Telegram и выключенных
  уведомлений при отсутствии Изменений, независимо от SQLite.
- При выключенном Telegram новые и ожидающие доставки получают нейтральное
  состояние `disabled` и не попадают в sender.
- Уже начатые доставки завершаются, исторические результаты не переписываются.
- Повторное включение не досылает старые Уведомления и немедленно проверяет
  доступность канала.
- Выключение во время перепроверки имеет приоритет над поздним результатом.
- «Telegram отключён» одинаково отображается без ошибки в Журнале, Истории
  Монитора и центре Уведомлений.
- При выключенном Telegram верхняя плашка остаётся зелёной, а карточка Telegram
  становится серой с точной согласованной подписью.
- Выключенный Telegram не предоставляет recheck или переход в настройки.
- Включённый недоступный Telegram по-прежнему ухудшает health и показывает
  причину с возможностью повторной проверки.
- Внутренние и браузерные Уведомления продолжают работать.
- Результаты Проверок, расписание, Снимки и История Мониторов не меняются.
- Старый HTTP update только с `notifyWhenUnchanged` остаётся валиден.
- `doctor` всегда продолжает проверять Telegram независимо от runtime-настройки.
- Новое состояние доставки поддерживается схемой SQLite, HTTP/OpenAPI, SSE и
  всеми UI-представлениями.
- Все новые переходы, гонки и регрессии покрыты автоматизированными тестами.
